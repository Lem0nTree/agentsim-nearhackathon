## October 21 and 22, 2026 — protocol, policy and research

- The first package included Node protocol and vault code, tests, a Rust contract scaffold, public reference material, a pitch and submission templates. The October 22 rerun recorded 32 passing tests. The deterministic agent driver and in-memory vault exercised the full grant/spend/revoke path. The accepted spend and settlement were local. See `docs/10-decisions-and-provenance.md`, `artifacts/test-results.txt`, `artifacts/demo-output.json`.
- An owner P-256 key signs domain-separated grant and control messages. Grant identity is the hash of its canonical bytes. Ed25519 signs each spend. Signed fields include chain, vault and epoch, plus an explicit recipient, limits and expiry. Compact JSON arrays have fixed field order; integers are decimal strings. The permission expires at the boundary itself. Monotonic nonces and stored grant identity prevent replay. Pause/resume, prospective revocation and owner rotation manage ongoing authority. Pending spends reserve funds before settlement. A failed transfer returns available funds once, while its nonce and allowance stay consumed. See `docs/03-protocol.md`, `src/protocol.mjs`, `src/vault.mjs`, `artifacts/protocol-vectors.json`.
- Residual risks include a compromised host displaying a different grant, stolen session keys using the permitted allowance, a relay censoring revocation, full-access account operators replacing code, callback failure, state growth, recovery and public linkability. The prototype provides no trusted display or independent lost-key recovery. See `docs/04-threat-model.md`.
- The planned NEAR vault verifies owner grants, agent spend requests and owner controls, reserves funds, dispatches a native transfer and handles a private callback. The Rust source originally had pinned direct dependencies without a resolved build, WASM, sandbox receipt or testnet transaction. October 21 RPC observations recorded mainnet protocol 86 and testnet protocol 87, with native P-256 host verification enabled on both queried endpoints. The NEP-635 source header then read Draft. The October 22 NEP index displayed Final. These dated editorial observations and network flags answer different questions. See `docs/05-near-integration.md`, `research/sources.md`, the two snapshot manifests and `contracts/agentsim-vault/`. [NEP-635](https://github.com/near/NEPs/blob/master/neps/nep-0635.md) · [nearcore config 85](https://github.com/near/nearcore/blob/2.13.0/core/parameters/res/runtime_configs/85.yaml)
- The application verifies raw P-256 over a SHA-256 digest. NEP-641 defines a separate signed envelope and recursive wallet-contract authorization resolution. WebAuthn adds authenticator data, challenge/origin, RP ID and presence/verification checks. Native NEAR access-key transactions use the outer transaction signer. NEAR Intents would introduce a distinct intent/settlement integration. Chain Signatures would add MPC authorization and cross-chain completion. None of these mechanisms is established by successfully verifying a raw P-256 signature. [NEP-641](https://github.com/near/NEPs/blob/master/neps/nep-0641.md)

## October 31 — connected development card

The authoritative chronological record is `tools/globalplatformpro/memory-probe/INVESTIGATION.md`. Its later entries supersede earlier inventory and memory snapshots. `tools/globalplatformpro/ecc-retest/src/agentsim/ecc/Ecc.java` defines the diagnostic and its response encoding.

1. The custom memory applet loaded, selected and executed. It reported 2,028 free persistent bytes while installed; the card manager independently returned the same value. With that probe removed, the manager reported 2,976 free persistent bytes and 3,268 free volatile bytes. The seller's family-level storage figures describe a different quantity.
2. The authenticated registry and comparison research identified preloaded packages. Two narrowly authorized deletions brought persistent free space from 2,976 to 43,444, then to 44,864 bytes. A small diagnostic again loaded and executed. After cleanup five original packages remained. These old authorizations apply to the recorded operations only.
3. A separate retest **after** the cleanup ran 16 cases. Fourteen EC operations returned `CryptoException` reason 3, `NO_SUCH_ALGORITHM`, at their first test stage. Cases covered FP key objects, key-pair creation, ECDSA and ECDH factories, other ECC sizes, transient/overload paths and the attempted known-scalar import. That import failed before the scalar or curve parameters could be applied. Two controls passed: SHA-256 of the standard public message and creation of an RSA-2048 public-key object. The control did not perform RSA generation or signing. The diagnostic APDU returned `9000` even when its result data reported a failed capability.
4. The authenticated descriptor's module bitmap and the actual API failures supported an ECC-disabled EMV configuration as the likely explanation for this unit. The family name, ATR resemblance and storage alone establish no manufacturer-certified SKU or particular seller intent. No supported procedure enabling ECC on this delivered unit was demonstrated. The probe was removed and the 44,864-byte result and five-package inventory were rechecked.
5. The older readiness note and early code handoff predated this post-cleanup ECC retest. Retain them as chronology. Use the later investigation for the October hardware outcome.
